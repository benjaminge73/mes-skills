# Le registre des garde-fous

Un correctif qu'aucun garde ne tient peut être défait sans que personne le voie :
la panne revient, et on la corrige une seconde fois. Ce registre tient la liste
**une ligne par règle** : ce qu'elle protège, d'où elle vient, **le garde qui la
tient** et où ce garde tourne.

Le principe : **chaque correctif reçoit un garde qui le rend impossible à défaire
sans que la CI le voie**, et le prochain correctif suit le même chemin — c'est la
règle de `CLAUDE.md`, section « Mettre à jour un skill ou un plugin » : tout
correctif ajoute sa ligne ici et son garde dans la même PR.

## Les règles

Le statut dit où en est le garde :

- **en place** : le garde existe et tourne. Le citer **en code** dans la colonne
  « Garde » — un fichier de script (`scripts/xxx.py`), un job de la CI
  (`ci.yml#nom-du-job`) ou un cas d'éval (`evals/<plugin>/<cas>`). Ce que la
  colonne cite est **vérifié** par `scripts/check_skills.py` : un garde cité qui
  n'existe pas refuse la PR ;
- **réglage** : le garde est un réglage GitHub, hors du dépôt, que rien ici ne
  peut vérifier ;
- **prévu — étape X** : le garde n'existe pas encore ; il dit l'étape qui le
  pose. Non vérifié ;
- **manquant** : la règle n'a pas de garde, et le registre le dit plutôt que de
  le taire. Non vérifié.

## Aucun skill ne porte `disable-model-invocation`

Le champ `disable-model-invocation: true` du frontmatter d'un skill interdit au
modèle de lancer ce skill de lui-même. La CLI Claude Code 2.1.331 le reconnaît et
le fait respecter (POC 4, plan skills externes #4, étape 9). Aucun `SKILL.md` du
dépôt ne le porte, et c'est voulu : les skills à effets de bord (écriture dans
Notion, publication, dépense) sont faits pour être lancés par le modèle dans un
plan ou une session, et le champ les bloquerait. Hermes, qui pilote aussi ces
skills, ne lit pas ce champ : il n'agirait que dans Claude Code, donc il ne
protégerait rien de façon homogène.

Décision Q10 (a), 2026-11-26 : pas de garde de forme sur ce champ, et pas de liste
d'exceptions dans `scripts/check_skills.py`. Si un skill doit un jour être réservé
au lancement par un humain, le champ se pose à ce moment-là, et la règle s'ajoute
ici avec son garde.

## Les hooks sont tous de type command

Décision Q14 (a), 2026-11-26 : les hooks des plugins sont tous de type command.
Constat vérifié le même jour : les 20 entrées de hooks déclarées dans les deux `hooks.json`
(18 dans `plans-notion`, 2 dans `nommage-sessions`) lancent 15 scripts locaux,
et aucun `plugin.json` ne déclare de hook. Un hook de ce type ne fait donc aucun
appel de modèle par lui-même. Le seul appel de modèle des hooks est celui que
pose `plugins/nommage-sessions/hooks/nommer_session.py` : le titrage d'une session
passe par `claude -p --model haiku`, une seule tentative par session, avec un délai
de 30 secondes, et ce titre reste un appel à `claude -p`, non un hook de modèle.
Un hook d'un autre type (prompt, agent) changerait la règle, et sa ligne s'ajouterait
ici avec son garde.

## Ajouter une ligne

1. Une règle, une ligne. Dire ce qu'elle protège **avec la panne qu'elle évite**,
   pas seulement le geste qu'elle demande.
2. Dater l'origine et la relier à sa source (plan, incident, PR).
3. Citer le garde **en code**, avec son chemin : c'est ce que `check_skills.py`
   vérifie. Un garde qu'on ne peut pas encore écrire prend « prévu — étape X » ou
   « manquant » — jamais un « en place » sans garde.
4. Ajouter le garde dans **la même PR** que la ligne.
